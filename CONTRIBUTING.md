# Contributing

Corrections are welcome, especially to the two things that matter most: the
astronomy and the rules.

## Reporting an error in the COLREGs content

Say which rule, what `colregs` says, and what the Convention says. Quote the
Convention text or cite the edition you are working from. The Convention is
right and this program is wrong; that is not a matter of opinion, so these get
fixed first.

## Reporting an error in the astronomy

Give a UT time, a body, and the value you expected with its source (a Nautical
Almanac page, JPL Horizons, or another ephemeris). `celnav alm "UT" body` prints
what this program computes, so a two-line issue is usually enough.

## Ground rules for code

1. **POSIX `sh` and POSIX `awk` only.** No bashisms, no GNU awk extensions.
   `gensub`, `asort`, `length(array)` and `%*d` in `printf` all break somewhere
   that matters. The test matrix runs `dash` and `bash` with `mawk` and `gawk`;
   BusyBox awk is a supported target too.
2. **No dependencies and no network.** These tools work in the middle of an
   ocean or they are not doing their job.
3. **Do not rely on `srand()`/`rand()`.** mawk re-seeds from the clock even when
   given an explicit seed. Use the `xsrand()`/`xrand()` generator in the engine.
4. **Edit `src/`, never `bin/`.** `bin/celnav` and `bin/colregs` are generated by
   `./build.sh` from the sources. A pull request that only changes `bin/` will be
   asked to move.
5. **Show the working.** If you add a computation, print its intermediate values.
   Someone at sea has to be able to check it by hand.
6. **Add a test.** `tests/run-tests.sh` is a plain shell script; a new check is
   usually three lines.

## Before you open a pull request

```sh
./build.sh
SHELLS="dash bash" AWKS="mawk gawk" ./tests/run-tests.sh
```

Both must pass. CI runs the same thing plus `shellcheck`.

## Style

Plain language in the user-facing text, and no exclamation marks. Explain why a
rule or a correction exists, not only what it is — the tools are meant to teach
as well as compute.


## Checking the rules, rather than the code

The test suite proves the programs work. It cannot prove that what they
say about the COLREGs, the almanac or the tides is true — a test can check
that a quiz marks answer C as correct, but not that C is right.

`colregs review` is the tool for that. It walks through every claim a test
cannot check — the encounter verdicts, the give-way calls, the twenty
light tables, the lesson answers, the sound signals and the day shapes —
one at a time, with the drawing in front of you, and records what you say.
When you are done it builds a report and prints a link that opens a GitHub
issue with your findings in it.

The program does not send anything. It has no network access at all, by
design and by test: `tests/run-tests.sh` fails the build if either tool
grows the ability to open a socket. You open the link yourself, and the
issue is signed by your own GitHub account — so a report is never
anonymous, and no email address is collected by anyone.

Credit is opt-in and name-only: see `CONTRIBUTORS.md`.

`tests/REVIEW.md` ranks what is worth checking by how much damage a wrong
claim would do. The short version: verdicts before light tables, because a
wrong light table makes you misname a ship and a wrong verdict makes you
turn the wrong way.
